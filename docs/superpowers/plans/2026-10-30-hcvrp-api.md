# API HCVRP (plan 2 de 3) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Servicio FastAPI con SQLite y login que guarda clientes, flota, parámetros, pedidos por fecha y bloqueos, y recalcula el plan en segundo plano usando el motor ya existente en `src/hcvrp/`.

**Architecture:** Paquete `hcvrp.api` encima del motor, que no se modifica salvo lo indicado.
- **Datos:** `sqlite3` de la biblioteca estándar, con las funciones de acceso en `store.py`.
- **Sesiones:** token aleatorio en una cookie HttpOnly.
- **Recálculo:** un hilo de fondo (`Recalculator`) agrupa cambios (debounce) y calcula el plan óptimo, la línea base y, si hay bloqueos, también el óptimo sin bloqueos. Guarda el resultado solo si corresponde al estado vigente de los datos.
- **Frontend:** el del plan 3 se servirá desde este mismo servicio, así que no hace falta CORS.

**Tech Stack:** Python 3.11, FastAPI, uvicorn, pydantic v2, sqlite3, httpx (ya está), OR-Tools (motor), pytest + `fastapi.testclient`.

**Spec:** `docs/superpowers/specs/2026-10-30-hcvrp-laguna-design.md` (§2 usuarios, §3 reglas, §5 datos, §6 comportamiento, §7 arquitectura). El motor está descrito en `docs/superpowers/plans/2026-10-30-hcvrp-motor.md`.

## Global Constraints

- `requires-python >=3.11`. Las únicas dependencias nuevas son `fastapi>=0.110` y `uvicorn>=0.29` (sin ORM, sin passlib, sin itsdangerous).
- Todos los textos que ve el usuario (errores, etiquetas) van en español.
- Rutas bajo `/api`. Todas exigen sesión salvo `POST /api/login`.
- La base de datos por defecto es `data/hcvrp.db` y se añade a `.gitignore`. Los datos reales de clientes nunca se versionan.
- Una fecha de plan es `YYYY-MM-DD` (`datetime.date`). Minuto 0 = 09:00.
- Las reglas de negocio (capacidad, jornada, costos, inviables) vienen solo del motor: `solve`, `baseline_plan`, `compare`, `validate`. La API no reimplementa ninguna.
- Un pedido por cliente por fecha: capturar otro para el mismo cliente suma sus kg al existente (spec §5.2). Así los bloqueos usan siempre el id del pedido guardado y `merge_orders` nunca descarta ids.
- Límite de cálculo: `Params.time_limit_s` (por defecto 15, editable entre 1 y 60). Las pruebas de la API fijan 1.
- Contraseñas con `hashlib.scrypt` (n=2**14, r=8, p=1, sal de 16 bytes), comparadas con `hmac.compare_digest`.
- Cookie `hcvrp_session`: HttpOnly, SameSite=Lax, `Secure` según `HCVRP_COOKIE_SECURE`. La sesión vence a los 30 días.

## Review Focus

1. **Cambios mientras calcula:** si los datos cambian durante un cálculo, ese resultado no reemplaza al plan mostrado. El plan anterior queda marcado como desactualizado hasta que llegue el del estado vigente (prueba en la Tarea 6).
2. **kg inválidos** (0, negativos, decimales, texto, más de 1 000 000): respuesta 422 con mensaje en español, y no se guarda nada (prueba en la Tarea 4).
3. **Borrados con dependencias:** borrar un pedido bloqueado borra su bloqueo, y borrar un cliente con pedidos responde 409 (pruebas en las Tareas 3 y 4).
4. **Bloqueo imposible** (camión no disponible, viaje que no cabe): el plan queda en estado `error` con el mensaje del motor, se conserva el último plan bueno marcado como desactualizado y el servidor sigue respondiendo (pruebas en las Tareas 5 y 6).
5. **Servicio de rutas caído o sin clave** (ORS 401, fallo de red, falta `ORS_API_KEY`): estado `error` con un mensaje legible, sin traza. Con `haversine` todo funciona sin red (prueba en la Tarea 7).

      - `get_fleet(conn) -> list[Vehicle]`, ordenada por `position`

      - `list_orders(conn, day: date) -> list[Order]`, con `order_id = str(id)`
      - `add_order(conn, day, client_code, kg) -> Order`: suma si ya existe.
      - `update_order_kg(conn, order_id: int, kg) -> Order`
      - `delete_order(conn, order_id: int) -> None`
      - `replace_orders(conn, day, orders: list[tuple[str, int]]) -> list[Order]`
      - `order_day(conn, order_id: int) -> date | None`
    - **Bloqueos:**
      - `get_locks(conn, day) -> dict[str, tuple[str, int]]`
      - `set_lock(conn, order_id: int, vehicle_id, trip_no) -> None`
      - `delete_lock(conn, order_id: int) -> None`
    - **Excepciones:** `class ClientInUse(Exception)`, `class NotFound(Exception)`.
  - `seed.main(argv) -> int`, invocado como `python -m hcvrp.api.seed [--clients data/clients_laguna.json] [--db ...]`:
    - inserta los clientes y convierte las direcciones `"NULL"` o vacías en `""`;
    - inserta la flota `DEFAULT_FLEET` y `Params()` solo si aún no existen;
    - es idempotente.

**Interfaces:**
- Consumes: `build_problem`, `inputs_hash`, `run_planning`, `PlanningError` (Tarea 5); `Settings` (Tarea 1).
- Produces:
  - En `store.py`:
    - `get_plan_row(conn, day) -> dict | None`, con `inputs_hash, status, result, error, computed_at`.
    - `save_plan_result(conn, day, inputs_hash, result: dict) -> None`: status `listo`, `error=NULL`.
    - `save_plan_error(conn, day, inputs_hash, message) -> None`: status `error`, conserva `result_json`.
    - `dates_with_orders(conn) -> list[date]`.
  - `make_provider(settings) -> DistanceProvider`: con `haversine` devuelve `HaversineProvider()`; con `ors`, `CachedProvider(OrsProvider())`.
  - `class Recalculator(settings, provider, geometry=None)`: un solo hilo daemon. Métodos:
    - `request(day: date | None) -> None`: `None` significa todas las fechas con pedidos.
    - `wait_idle(timeout: float = 60) -> bool`.
    - `is_busy(day) -> bool`: verdadero mientras esa fecha está pendiente o en cálculo.
    - `pause()` / `resume()`: ganchos de prueba, un `threading.Event` que el hilo espera antes de cada cálculo.
    - `stop() -> None`.
  - Algoritmo del hilo, para cada fecha pendiente:
    1. Espera `debounce_s` sin nuevas peticiones para esa fecha.
    2. Abre su propia conexión y calcula `h = inputs_hash(build_problem(...))`. Si el plan guardado ya tiene ese hash con status `listo` o `error` y la petición no fue forzada, termina sin recalcular.
    3. Ejecuta `run_planning`.
    4. Vuelve a calcular el hash vigente. Si cambió, descarta el resultado y encola la fecha otra vez. Si no cambió:
       - guarda con `save_plan_result`;
       - con `PlanningError` o `RuntimeError`, guarda con `save_plan_error(str(e))`;
       - con cualquier otra excepción, guarda `"error interno al calcular el plan"` y la registra con `logging.exception`.

    El hilo nunca muere.
  - `create_app`:
    - crea el `Recalculator` con el provider de `make_provider` y lo guarda en `app.state.recalc`;
    - define `app.state.on_change = recalc.request`;
    - lo detiene al apagar, en el lifespan.
  - **Rutas:**
    - `GET /api/plan?date=` responde `{"status": "ninguno"|"calculando"|"listo"|"error", "stale": bool, "error": str|None, "plan": PlanOut|None, "computed_at": str|None}`:
      - `stale` es verdadero si existe un plan guardado y su hash difiere del vigente.
      - `status` es `calculando` si `is_busy(date)`, o si hay pedidos y el hash guardado no coincide con el vigente.
      - Un día sin pedidos ni plan responde `ninguno`.
      - Si no hay pedidos pero sí un plan anterior, conserva el status guardado (`listo` o `error`) con `stale=true`.
    - `POST /api/plan/recalcular?date=` responde 202 y fuerza el recálculo aunque el hash coincida.
